# mod-409 — Agent-to-Agent Routing and Inter-Agent Service Mesh

**Estimated effort:** 10 hours · **Position in track:** ninth module (after [`mod-401`](../mod-401-agent-platform-position-and-paved-road-philosophy), [`mod-402`](../mod-402-agent-runtime-service-and-durable-execution), [`mod-403`](../mod-403-mcp-registry-and-tool-gateway), [`mod-404`](../mod-404-sandboxed-code-execution-plane), [`mod-405`](../mod-405-tool-and-permission-policy-plane), [`mod-406`](../mod-406-model-gateway-and-routing), [`mod-407`](../mod-407-evaluation-platform-and-regression-gating), [`mod-408`](../mod-408-observability-and-opentelemetry-for-agents)).

Every module up to this one has reasoned about one agent: one loop, one process, one identity, one trace. The moment agents start calling other agents — a writer agent handing off to a researcher, a supervisor agent routing to a coder, a sales agent delegating to a finance agent across tenants — a new plane shows up. The things that used to be in-process (the identity of the caller, the permissions that follow them, the correlation id on the trace, the fallback when a dependency hangs) are now on the wire. And the wire is the platform's problem. This module takes [Agent2Agent (A2A)](https://a2a-protocol.org/) — an open protocol for agents to discover each other, exchange tasks, stream updates, and delegate work — and maps it onto the service-mesh primitives (Istio/Envoy, Linkerd, SPIFFE/SPIRE, OAuth 2.0 token exchange) already in play. By the end you can stand up an inter-agent routing plane that preserves correlation, delegates identity with audit, narrows permissions on every hop, isolates failures with circuit breakers and bulkheads, and offers both *handoffs* and *manager-as-tools* topologies without re-inventing a framework.

## Learning objectives

- Read the [Agent2Agent (A2A) protocol specification](https://a2a-protocol.org/) and map it to the platform's existing service-mesh primitives — Istio/Envoy routing, Linkerd, SPIFFE workload identity, mTLS, xDS.
- Engineer inter-agent routing with service discovery (the agent registry and AgentCard), correlation-ID propagation (`traceparent` + baggage), user-identity delegation ([RFC 8693 token exchange](https://datatracker.ietf.org/doc/html/rfc8693)), permission-scope propagation (narrowing by callee AgentCard), and tenant isolation (three-layer enforcement at registry, mesh, and scaffold).
- Apply circuit breakers (Envoy outlier detection + per-upstream state machines), bulkheads (per-upstream connection and concurrency isolation), retry budgets, and deadline propagation to inter-agent dependency graphs so that one slow leaf agent does not cascade to the fleet.
- Reason about *handoffs* vs. *manager-as-tools* topologies, the platform-level primitives each requires (durable state transfer and session-affinity rewrite for handoffs; per-subagent concurrency budgets and fan-out circuit-breaker policy for manager-as-tools), and the characteristic failure modes of each.
- Hand off cleanly to `agentic-systems-architect` (level 48) for multi-agent *design* and to `senior-agentic-ai-engineer` (level 40) for product-side subsystem implementation, with explicit contracts in both directions.

## How to approach this module

1. Read the six chapters in order. The slice (01) is the frame; the protocol-and-mesh mapping (02) is the structural centre everything else attaches to; routing and discovery (03), identity (04), and resilience (05) are the three operational concerns; topology (06) closes with the role boundaries you will negotiate as the plane matures.
2. Do exercise 01 before reading chapter 04. Chapter 04's identity flow is easier to follow once you have seen the A2A surface the flow sits on.
3. Do exercise 02 before exercise 03. The breakers you tune in exercise 03 assume the identity and tenant checks from exercise 02 already work; re-debugging a token-exchange failure while also tuning an outlier-detection threshold is one problem too many.
4. Keep the chapter 01 `A2ACallRecord` shape open while reading the rest. Every chapter adds a field; losing the record as the connective tissue is how the plane devolves into a tangle of mesh YAML and framework-specific glue.
5. Mark `<!-- needs-research: ... -->` on any claim you cannot verify. The A2A spec moved to the Linux Foundation in 2025 and is still iterating; the OAuth 2.0 token-exchange support in commodity authorisation servers is uneven; the mesh CRD field names shift across versions. The flag convention is consistent with mod-403 / 404 / 405 / 406 / 407 / 408 and blocks auto-merge, which is cheaper than silently guessing.

## Where the handoffs land

- **`agentic-systems-architect` (peer, level 48)** — owns multi-agent *design*: which topology for which product, which agents compose into which chains, when to add a new agent to the fleet, when to deprecate one. The plane engineer's handoff is framework-and-topology-parity primitives, an AgentCard review cadence, a joint dependency-graph review before new inter-agent edges activate, and an escalation path for patterns the plane does not yet support. Chapter 06.
- **`senior-agentic-ai-engineer` (peer, level 40)** — owns the product-side subsystem implementation: the agent's handler, prompts, tools, loop logic, framework choice, eval harness. The plane engineer's handoff is paved-road A2A client and server scaffolds, the AgentCard as a contract the scaffold enforces, a pre-registry conformance test the agent must pass, and a replay-and-dashboard interface for the on-call escalation path. Chapter 06.
- **`ai-infra-sre` (peer, level 40, mod-410)** — consumes the plane's resilience signals (breaker state, retry rate, deadline-exceeded count, bulkhead saturation) and runs the alerting + runbook + post-incident loop. Chapter 05.
- **`agentic-safety-engineer` (peer, level 40, mod-411)** — emits guardrail verdicts on inter-agent handoffs when the handoff would send a user to a less-safe agent. The plane provides the hook; the safety plane authors the policy. Chapter 06 and cross-reference mod-411.
- **`agent-platform-leadership` (mod-413)** — owns the governance cadence that reviews the registry's `cross_tenant_allow`, the fleet-wide fan-out shape, and the audit-stream retention. The plane is the mechanism; governance is the accountability. Chapter 04 and 06, cross-reference mod-413.
- **Observability plane (mod-408)** — upstream dependency on `gen_ai.*` semconv, `traceparent` propagation, and the collector tier. Every chapter in this module assumes mod-408 is in place.

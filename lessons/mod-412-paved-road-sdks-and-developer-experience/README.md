# mod-412 — Paved-Road SDKs, Templates, and Developer Experience

**Estimated effort:** 12 hours · **Position in track:** twelfth module (after [`mod-401`](../mod-401-agent-platform-position-and-paved-road-philosophy), [`mod-402`](../mod-402-agent-runtime-service-and-durable-execution), [`mod-403`](../mod-403-mcp-registry-and-tool-gateway), [`mod-404`](../mod-404-sandboxed-code-execution-plane), [`mod-405`](../mod-405-tool-and-permission-policy-plane), [`mod-406`](../mod-406-model-gateway-and-routing), [`mod-407`](../mod-407-evaluation-platform-and-regression-gating), [`mod-408`](../mod-408-observability-and-opentelemetry-for-agents), [`mod-409`](../mod-409-agent-to-agent-routing-and-service-mesh), [`mod-410`](../mod-410-reliability-engineering-and-sre-for-agents), [`mod-411`](../mod-411-safety-plane-and-guardrails-as-a-service)).

Every prior module in the track stood up a plane and left behind a seam the SDK is meant to pave. The runtime (mod-402) exposes the `SessionState` contract. The MCP gateway (mod-403) catalogues tools behind a resolve API. The sandbox (mod-404) offers a scoped execution client. The policy plane (mod-405) decides permissions on identity. The model gateway (mod-406) routes completions. The evaluation plane (mod-407) catalogues fixtures. The observability plane (mod-408) fixes the semantic vocabulary. The inter-agent plane (mod-409) carries A2A edges. The SRE plane (mod-410) runs the fleet. The safety plane (mod-411) guards each turn with three hooks. This module asks the question none of them finish: *how does a stream-aligned product team adopt all of the above without wiring eleven planes into every agent repo by hand, and how does the platform measure whether its paved road is actually being used?*

That is the slice this module owns. By the end you can author a paved-road agent SDK whose reference shapes compose the five mainstream agent frameworks ([Anthropic Agent SDK](https://docs.anthropic.com/en/api/agent-sdk/overview), [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/), [Google Agent Development Kit](https://google.github.io/adk-docs/), [Microsoft Agent Framework](https://learn.microsoft.com/en-us/agent-framework/overview), [LangGraph](https://langchain-ai.github.io/langgraph/) on [Temporal](https://docs.temporal.io/)) into a single opinionated shape, ship a scaffolding CLI and template catalogue in the shape the [CNCF Platforms whitepaper](https://tag-app-delivery.cncf.io/whitepapers/platforms/) and [Backstage Software Templates](https://backstage.io/docs/features/software-templates/) have standardised, stand up a local-dev loop with sandbox emulation, a trace viewer, and offline eval replay, publish a CI template that fills the five paved-road gates (lint, unit, eval regression, safety, cost), expose a standardised instrumentation hook library that fills `gen_ai.*` and `platform.*` span attributes automatically, define and measure the four adoption KPIs the [CNCF Platform Engineering Maturity Model](https://tag-app-delivery.cncf.io/whitepapers/platform-eng-maturity-model/) scores Interfaces and Adoption against (platform adoption rate, time-to-first-agent, deployment success rate, rollback count), and operate the enablement cadence — onboarding sessions, office hours, migration playbooks, deprecation ladders — that turns the paved road into the *default* road rather than the *mandated* road.

## Learning objectives

- Author the paved-road agent SDK and templates — reference shapes using [Anthropic Agent SDK](https://docs.anthropic.com/en/api/agent-sdk/overview), [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/), [Google Agent Development Kit](https://google.github.io/adk-docs/), [Microsoft Agent Framework](https://learn.microsoft.com/en-us/agent-framework/overview), and [LangGraph](https://langchain-ai.github.io/langgraph/) + [Temporal](https://docs.temporal.io/).
- Ship scaffolding CLI, local-dev loop (sandbox emulation, trace viewer, offline eval replay), CI templates, standardised instrumentation hooks aligned to [OpenTelemetry Semantic Conventions for Generative AI](https://opentelemetry.io/docs/specs/semconv/gen-ai/).
- Define and measure adoption — platform adoption rate, time-to-first-agent, deployment success rate, rollback count — informed by the [CNCF Platform Engineering Maturity Model](https://tag-app-delivery.cncf.io/whitepapers/platform-eng-maturity-model/) indicators for Interfaces and Adoption.
- Operate office-hours, migration playbooks, deprecation ladders, and the enablement cadence that turns the paved road into the default road — framed by [Team Topologies](https://teamtopologies.com/) and the [DevEx framework](https://queue.acm.org/detail.cfm?id=3595878) (Noda, Forsgren, Alexander, Storey).
- Hand off to [`agentic-ai-engineer`](../../../agentic-ai-engineer-learning/) (level 30) as the primary builder adopting the paved road and to [`senior-agentic-ai-engineer`](../../../senior-agentic-ai-engineer-learning/) (level 40) as the subsystem-lead consumer who negotiates the escape hatches.

## How to approach this module

1. Read the seven chapters in order. The slice (01) is the frame; the framework reference shapes (02) are the SDK's core shape; the scaffolding CLI (03) is the first thing a stream-aligned engineer touches; the local-dev loop (04) is the point at which they decide whether the paved road is worth it; the CI gates and instrumentation hooks (05) are what makes the road survive production; the adoption KPIs (06) are how the platform proves the road is being used; the enablement cadence (07) is how the road becomes the default rather than the mandated route.
2. Do exercise 01 before reading chapter 04. The moment you try to produce a working sample agent from the reference shape, the pain points of "what does `SessionState` look like under the Anthropic SDK vs. the OpenAI SDK" surface in a way reading alone will not reveal.
3. Do exercise 03 after chapter 06 — the adoption formulas are the artefact the exercise commits to. Writing dashboards before pinning the formulas lands you with vanity metrics that chapter 06's cadence section will call out.
4. Keep the chapter 01 `AgentRevision` manifest shape open while reading the rest. Every chapter adds a field; losing the manifest as the connective tissue is how the paved road devolves into a sample repo and a Slack channel.
5. Mark `<!-- needs-research: ... -->` on any claim you cannot verify. The specific attribute names in [OpenTelemetry Semantic Conventions for Generative AI](https://opentelemetry.io/docs/specs/semconv/gen-ai/), the Anthropic Agent SDK / OpenAI Agents SDK / Google ADK / Microsoft Agent Framework release-version numbers, the [Backstage Software Templates](https://backstage.io/docs/features/software-templates/) template-spec field names, the [Cookiecutter](https://cookiecutter.readthedocs.io/) and [Copier](https://copier.readthedocs.io/) hook names, and the CNCF maturity-model level descriptions all shift version-to-version. The flag convention is consistent with `mod-403 / 404 / 405 / 406 / 407 / 408 / 409 / 410 / 411` and blocks auto-merge, which is cheaper than silently guessing.

## Where the handoffs land

- **[`agentic-ai-engineer`](../../../agentic-ai-engineer-learning/) (peer, level 30)** — the primary consumer of the paved road. The SDK's contract to them is "importing `paved_road_agent` wires you into every plane with one function call and a `manifest.yaml`; the scaffolding CLI gets you from `clone` to first turn in ninety seconds; the local-dev loop runs offline". Their contract to the SDK is "we adopt the scaffolder as the starting point for new agents and we file issues against the SDK rather than forking". Cross-reference chapters 02, 03, 04.
- **[`senior-agentic-ai-engineer`](../../../senior-agentic-ai-engineer-learning/) (peer, level 40)** — the subsystem-lead consumer who negotiates the escape hatches. The SDK's contract to them is "the adapter boundary is explicit; when you need framework-specific behaviour the paved road cannot express, the exception register is a documented, auditable mechanism and the roadmap conversation is open". Their contract to the SDK is "the exception register is the forcing function back onto the paved road, not an indefinite license to fork". Cross-reference chapters 02 and 07.
- **Runtime plane (mod-402)** — upstream dependency on the `SessionState` contract, the checkpoint envelope shape, and the framework-adapter surface. The SDK's five adapters sit on mod-402's unified session-state abstraction. Cross-reference chapter 02 and mod-402 chapter 04.
- **MCP gateway (mod-403)** — upstream dependency on the tool-resolution API and the tool metadata schema. The SDK's tool-call hook imports mod-403's client. Cross-reference chapter 02.
- **Sandbox (mod-404)** — upstream dependency on the sandbox client and the sandbox emulator used in the local-dev loop. Cross-reference chapter 04.
- **Policy plane (mod-405)** — upstream dependency on the identity-and-permission hook the SDK invokes before each tool call. Cross-reference chapter 02 and 05.
- **Model gateway (mod-406)** — upstream dependency on the routing client. The SDK's completion hook sends completions through mod-406. Cross-reference chapter 02.
- **Evaluation plane (mod-407)** — upstream dependency on the fixture catalogue and the regression harness. The SDK's CI template ships the eval-regression gate; the local-dev loop ships offline replay against the catalogue. Cross-reference chapters 04 and 05.
- **Observability plane (mod-408)** — upstream dependency on the `gen_ai.*` and `platform.*` semantic conventions. The SDK's instrumentation hook library is the conformance surface that keeps those attributes consistent across agents. Cross-reference chapter 05 and mod-408 chapter 02.
- **Inter-agent plane (mod-409)** — the SDK's A2A client imports mod-409's circuit breaker and retry budget. Cross-reference chapter 02.
- **SRE plane (mod-410)** — upstream dependency on the `ReliabilityRecord` emitter and the burn-rate alert vocabulary. The SDK's CI template and the adoption dashboard both link to mod-410's SLO document templates. Cross-reference chapters 05 and 06.
- **Safety plane (mod-411)** — upstream dependency on the three hook invocations (input filter, output validator, tool-invocation policy hook). Importing the SDK opts an agent into the safety plane with no manual wiring, satisfying the mod-411 obligation. Cross-reference chapter 02 and mod-411 chapter 01 obligation 1.
- **Platform leadership (mod-413)** — owns the operating cadence over the adoption scorecard (chapter 06) and the deprecation-ladder sign-offs (chapter 07). The SDK is the mechanism; leadership is the accountability. Cross-reference chapter 06 and mod-413.

## Scope policing

The paved-road SDK plane does **not** own: the runtime substrate (mod-402), the tool catalogue itself (mod-403), the sandbox implementation (mod-404), the policy engine (mod-405), the model routing logic (mod-406), the eval fixtures and judge calibration (mod-407), the semantic-conventions spec (mod-408), the A2A routing substrate (mod-409), the SLI / SLO / error-budget policy (mod-410), the guardrail engines or policy packs (mod-411), nor product-side agent correctness ([`senior-agentic-ai-engineer`](../../../senior-agentic-ai-engineer-learning/), [`agentic-ai-engineer`](../../../agentic-ai-engineer-learning/)). Drift off this slice and the SDK becomes "the team that writes everyone else's agent code" — a feature team with a confused name, not a platform plane. Chapter 01 pins the scoping story; chapter 07 enforces it against the "just add this one thing to the SDK" pressure.
